# DESIGN §27 — Accounts, friends and quick invites

Part of [DESIGN.md](../DESIGN.md) (the index; section numbers are global).

## 27. Accounts, friends and quick invites

An **account** is a public identity for the social layer only — the name another player sees in a friends list, a friend request or an invite. It is **not** the identity of the room or the battle: the session's per-connection `playerId` (`server/net.js`) stays what a room seat, a match and every reconnect token are keyed on, and `server/match/**` never sees an account id. The account is bound to the session (`session.accountId`) and only the lobby reads it (`server/lobby.js`), so an account can be added without touching the match engine at all. **Guests remain first-class**: with no account a player creates and joins rooms, plays solo or co-op, sends emotes and reconnects exactly as before. Accounts are opt-in and gate only the social features — friends, quick invites, presence and share links. A deployment can even run with no account layer (`accounts: null`): every social intent then answers `ACCOUNT_REQUIRED` and the rest of the lobby is unchanged.

The design is the owner's requirement of 2026-10-08 (a public deployment needs a way for friends to find each other without passwords) and it is deliberately narrow: identity without a username, a password, an e-mail or recovery, and a friend graph with **exactly one door** — the people a player demonstrably played a match with. Everything social hangs off the account **id** (`a_` + 20 hex characters = 80 random bits; a public, non-secret handle), never off a `playerId`. `server/accounts.js` owns every rule about who may be friends with whom and is deliberately transport-agnostic; `server/lobby.js` owns the wire side, the room-derived presence and the share link.

### 27.1 Share links and the reported origin

A public deployment almost always sits behind an frp-like reverse tunnel (cloudflared, frp, Tailscale Funnel, nginx, a router port-forward), so the server **cannot know** which address the player actually reached it by — a LAN IP, a tunnel hostname, a domain. The browser does know it (`location.origin`), and the official client behaves the same way: the invite link is the page's own URL plus `?room=CODE`. The client therefore reports its origin and the server turns it into the canonical link other players are handed. This is the one part of §27 a deployment configures, so it is stated first.

The risk `shared/origin.js` exists to contain: a client-supplied origin is attacker-controlled input, and whatever the server echoes back can end up in **someone else's** clipboard. The rule is:

- The canonical form is computed with the WHATWG URL parser and compared strictly (`canonicalOrigin`): a value with a path, a query, a fragment, credentials, a non-http(s) scheme, a hostname longer than 255 characters or more than `ORIGIN_MAX_LEN` (128) characters is rejected outright, so a link can never smuggle `?room=`, `#` or a second URL inside itself. The protocol validator (`shared/protocol.js isOriginField`) accepts only an already-canonical value, which the browser's `location.origin` always is.
- An origin is accepted only when it **equals the origin this very connection arrived on** — the `Host` header, or `X-Forwarded-Host` / `X-Forwarded-Proto` when the peer is a trusted reverse proxy (`server/net.js connectionOrigin`, the same trust rule as `clientAddress`: a loopback/private peer, or `TRUST_PROXY=1`). That is the address the player demonstrably used.
- A deployment that knows its public address pins it with `SP_PUBLIC_ORIGINS`, and that list is then **EXCLUSIVE**: an unlisted origin is refused even when the connection came in on it. This is what stops a player from pointing their own tunnel at the server and handing out links through it.
- The server **never broadcasts an origin to other players**. Every session gets its own answer (`welcome.shareOrigin`, and the `share.link` reply), and the client (`public/js/account.js`) falls back to its own `location.origin` when the server has no opinion. A wrong answer therefore cannot make the game hand out a link to somebody else's address.

`share.link {}` answers through the `ok` payload (`{origin, url, code, source}`): `url` is `${origin}/?room=<code>` (the code `encodeURIComponent`-escaped) in a room and `${origin}/` otherwise, `source` is `'allowlist'` (pinned by the operator), `'connection'` (the address this player used) or `'none'` (no server opinion; the client builds the link itself). `pickShareOrigin` falls back from the reported origin to the connection's own canonical origin, so a client that reported nothing (or something stale) still gets a usable link. `SP_SHARE_LINK=0` makes `resolveOrigin` return null: no canonical link is offered at all and the client uses its own address.

The attack this blocks is concrete: without the rule a member of a room could mint `https://evil.example/?room=CODE` as "the game's own share link" and a victim clicking it would land on a look-alike page; and a player who runs a tunnel pointed at the server could hand out links whose origin is their own hostname. With the equality rule the first is refused (it is not the connection origin), and with a pinned allowlist the second is refused too (it is not listed).

### 27.2 The account key

`shared/accountKey.js` defines the credential. `create()` mints **160 bits** of CSPRNG entropy (`node:crypto randomBytes(20)`) and renders them in **Crockford base32** — the alphabet drops `I`, `L`, `O` and `U`, so a hand-copied key has no ambiguous characters. A canonical key is 32 characters, **displayed as 8 groups of 4** separated by `-` (`XXXX-XXXX-…`, 39 characters, e.g. `4ZQK-8M2P-…`). Parsing (`canonicalKey`) is case-insensitive and tolerates the separators `-`, space, tab and `_`, and maps the rarely hand-typed Crockford confusables (`I`, `L` → `1`; `O` → `0`; `U` → `V`) — lossless, because a canonical key never contains them. `formatKey` renders the display form; `KEY_MAX_LEN` (64) is the protocol field limit, `KEY_CHARS` (32) the canonical length.

**There is no password, no e-mail and no recovery: the key IS the account.** It is returned exactly once, by `account.create` or `account.rotate`, and the player is told to keep a copy; the browser also caches it in `localStorage` (`sp.account`), so a reload, a new tab and a reconnect stay logged in. Anyone holding the key holds the account, so the whole account-security story reduces to (a) the key never leaks past its owner, (b) only a digest is ever stored server-side, and (c) the endpoints that accept it are rate limited (see §27.8).

The server keeps accounts in a `Map` keyed by the **peppered SHA-256 digest** of the canonical key: `hashKey = sha256(SP_KEY_PEPPER + '\u0000' + canonical)` when a pepper is set, and the canonical key alone otherwise (`server/accounts.js hashKey`). The persistence file therefore contains digests only and cannot be replayed even if leaked; the pepper additionally makes the file useless against a *different* deployment. `account.login` looks the digest up in a `Map`, and an unknown key and a malformed key answer the **same** `ACCOUNT_BAD_KEY`, so the endpoint is not an oracle for whether an account exists. The account id is `a_` + 20 hex characters; `accountTag` is its last four characters, the short public discriminator a UI shows next to a name (`Fang #7C3A`) so two similar-looking names stay distinguishable.

Display names get the same care, because a stored, unique, friend-visible string is a squatting target: `normalizeName` NFKC-composes circles/ligatures/full-width characters, strips `INVISIBLE_RE` (C0/C1 controls, soft hyphen, zero-width and bidi controls, BOM, interlinear annotation marks — the classic way to make two different names render identically), collapses whitespace runs, trims and caps at `NAME_MAX_LEN` (12) code points; a name with nothing displayable left is refused. `nameKey` is the display form case-folded with `toLowerCase`, and a name collision answers `NAME_TAKEN`, so `Fang`, `fang` and `ＦＡＮＧ` are one account name.

### 27.3 `account.create` / `login` / `rename` / `rotate` / `logout`

- **`account.create {name}`** mints the key, stores the record and binds the session (`session.accountId`, `session.name = account.name`). The session receives `account.state` with the freshly minted `key` (the only place it is ever sent), then `friend.state`. Refusals: an empty/normalisable-to-nothing name is `BAD_MSG`, a taken name is `NAME_TAKEN`, the global cap `MAX_ACCOUNTS` (5000) is `TOO_MANY`, and a per-network creation cap (`CREATE_PER_ADDR_PER_HOUR` 20/hour per `session.limitKey`, a bounded map) is `RATE`. A session that already has an account gets `ALREADY`.
- **`account.login {key}`** proves a key and binds the session; `hello.key` does the same thing at handshake time (see §27.10), and `hello.key` may *switch* a session to another account. A session that presents no key keeps whatever account it already had, so a plain reconnect never logs anyone out. The **account name is authoritative over the title-screen nickname**: the store name becomes `session.name`, and an existing LOBBY seat's visible name and `room.state` are updated in step (exactly like a reconnect rename; a match in progress keeps its seats). Unknown/malformed keys answer `ACCOUNT_BAD_KEY`; too many failures from one socket answer `RATE` (the per-session throttle, §27.8). A refused `hello.key` is echoed once as `welcome.accountError`, and the client drops its cached key and prompts for a new one.
- **`account.rename {name}`** renames the one account name; uniqueness is `nameKey`, collisions are `NAME_TAKEN`, and renaming to the same name is a no-op `ok`. The session name, a LOBBY seat's name and every friend's/invite's view follow immediately (`account.state`, `friend.state`, and a force-pushed presence so friends see the new name).
- **`account.rotate {}`** mints a fresh key and unindexes the old digest, so the old key **stops working immediately** — the "my key leaked" button. Every OTHER live session of the account is dropped: its `accountId` is cleared, `accountError` is set to `ACCOUNT_BAD_KEY`, and the socket is closed with WebSocket close code **4004** (`server/net.js CLOSE.ROTATED`, `public/js/net.js CLOSE_ROTATED`). The requesting session keeps its login and receives the new key once, in `account.state`.
- **`account.logout {}`** makes *this session* stop using the account; the **key stays valid** (only `account.rotate` kills a key), so it is the "shared computer / hand the laptop over" button. The session keeps its nickname and its seat, and its friends see the account go offline (unless another session of the account is still online).

The title screen is a **guest** until the player enters the shell: its socket is open but has not said `hello`, and `net.request` refuses everything with `OFFLINE`. Every account action taken there therefore goes through `public/js/account.js account.online()` first, which says hello itself — with the typed call-sign, or with a generic placeholder when logging in with a key (the server replaces it with the account's own name the moment the key binds, so it is never visible). A **cached key is bound at boot** for the same reason (`public/js/main.js`), so the title screen's friends panel, its presence and the 快速邀请 popups work without pressing 开始; the title call-sign field is filled from the logged-in account's name, and `hello.key` is what carries the cached key.

### 27.4 The one and only friend door (`recordPlayed`)

There is deliberately **no search, no add-by-name and no add-by-id channel**. The only accounts a player may ask to be friends with are those in the **played-together ledger**, and the ledger is written when a match **STARTS** — `server/lobby.js` calls `accounts.recordPlayed(accountIdsOf(room))` at `startMatch`, which is the moment the room's human players demonstrably entered the same battle. The input is the account ids of the human players **seated** in the room; bots, spectator seats and players who left are excluded, and a player without an account contributes nothing (and records nothing).

`recordPlayed` writes the ledger **pairwise**: for every ordered pair of distinct accounts it stamps `playedWith[other] = now`, newest wins, and each account is pruned to `MAX_MET` (200) **newest** partners. An edge is usable for `MET_TTL_MS` (90 days); after that an old teammate can no longer be friended — the owner's rule is "only people you played with", bounded in time as well as in count. `isEligible` is the single check `friend.request` runs, and `metList` is what a client sees as addable: eligible partners that are not already friends and have no pending request in either direction, newest first (`friend.state.met`).

`friend.request {accountId}` refuses with `NOT_ELIGIBLE` unless the pair is (or recently was) in that ledger. Otherwise: a non-existent target or self is `BAD_TARGET`; already friends is `ALREADY`; a target who recently declined this account is `DECLINED` (a `DECLINE_COOLDOWN_MS`, 7-day, cooldown stored on the decliner so "request → refuse → request" cannot be used as a notification channel); an incoming request from that very account is treated as **acceptance** (a mutual request needs no second round trip); a duplicate outgoing request is `ALREADY`. Caps apply and answer `TOO_MANY`: `MAX_FRIENDS` (100) on either side and `MAX_PENDING_REQUESTS` (50) outgoing/incoming. The sender gets a fresh `friend.state`; the target gets the `friend.request {accountId, name, at}` push and a toast.

Requests need acceptance: `friend.accept {accountId}` links both sides (`#link`), which clears every pending direction between the two and answers `TOO_MANY` if either list is full; a pending request of one's own is **not** consent, so accepting a request that does not exist is `BAD_TARGET` even then (the only consent-free case — both sides asked — is handled inside `friend.request`, which can see both directions). `friend.decline {accountId}` refuses an incoming request (or withdraws one's own), removes the pending state on both sides and sets the decliner's cooldown. `friend.remove {accountId}` lets **either** side delete the edge, which disappears on both, and clears any pending state. Both sides always see the change: a removal sends the other side `friend.remove {accountId, name}` plus a fresh `friend.state`, and a new friendship sends both sides `friend.state` and force-pushed presence.

### 27.5 Presence (`friendSnapshot` / `presenceOf`)

`friend.state` is the whole social snapshot for one account: `{account, friends, incoming, outgoing, met, invites}`. Every `friends` entry is `presenceOf`'s answer: `{accountId, name, online, status, room}` with the exact status vocabulary

- `offline` — no connected session of the account;
- `idle` — online, not in a room;
- `lobby` — in a room whose match has not started (joinable when a seat is free);
- `match` — in a running match (only watching is possible);
- `solo` — in a solo run, which can be neither joined nor watched, so only the fact of it is shared;
- `hidden` — in a room created with 屏蔽好友 (see §27.6).

`room` is present only when it may be shown, and holds exactly `{code, mode, difficulty, players, joinable, spectatable}` — `players` is the number of active humans, `joinable` is `!room.match && room.freeSeat() >= 0`, and `spectatable` is `room.spectators.length < MAX_SPECTATORS` (2). A room code is the ability to join, so it is shown only to the friends of a member and never for a hidden room.

Presence is **coalesced**: `notifyFriends` pushes at most one presence frame per account per `friendPushMs` (default 1000 ms), with a timer that collapses a burst, and `force` skips the throttle for events that must be seen at once (a relationship or name change, a logout, a room disposal). Frames are additionally **content-deduped**: the last frame per account is kept (`presenceFrames`, bounded) and an unchanged frame is not sent, so a ready toggle or a seat switch that re-broadcasts the room costs nothing on a friend's socket. Because every visible room change ends in `broadcastState` → `notifyMembers`, the members' friends keep the occupancy and status in step without the room code ever being broadcast.

What is deliberately **NOT** in a presence frame: a friend's seat position, loadout, ownership, 自选 picks, host status, the names or number of the other members, the room code of a hidden room, and anything about a solo run beyond the status `solo`. A presence frame is derived from the rooms the lobby owns (`server/lobby.js presenceOf`), never from account-store data alone, and it is never a private view of the room.

### 27.6 屏蔽好友 (hidden rooms)

`room.create {hidden:true}` sets `room.hideFromFriends` at creation (it is fixed for the room's life; `lobby.create` logs it). The creator's friends then see `status: 'hidden'` with `room: null` — they learn only "not available". This is the owner's requirement 创建对局时允许屏蔽好友: presence is a broadcast, and a player may decline to be found by it. An explicit `invite.send` to a chosen friend **still works** from a hidden room: that is a deliberate act rather than a broadcasting one, and the invite carries the room code to that one recipient. Solo runs are never shown with a room either, hidden or not.

### 27.7 Quick invites

`invite.send {accountId}` asks the server to deliver an invitation to the room this session is in to one friend. The sender must have an account, be **in a room** (`NOT_IN_ROOM`), not in a match (`ROOM_STARTED`), in a co-op room (a solo room answers `ROOM_FULL`), with a free seat (`ROOM_FULL`), and not be a spectator (`SPECTATOR`); the recipient must be a mutual friend (`NOT_FRIEND`).

`createInvite` mints a **recipient-bound random** id `i_<hex>` (12 random bytes = 96 bits) — useless to anyone else and unguessable — with a lifetime of `INVITE_TTL_MS` (120 s). A per-pair cooldown (`INVITE_COOLDOWN_MS`, 20 s, a bounded map) answers `RATE 'just invited'`; the cap `MAX_INVITES_OUT` (20 open invites per sender) answers `TOO_MANY`. Once that cooldown has passed, re-inviting the same friend for the **same room** refreshes the existing invite (`at`, `expiresAt`, `players`) instead of stacking a second one. The recipient is shown at most `MAX_INVITES_IN` (10) at once; older ones are dropped first.

Delivery reaches **every live session** of the recipient account (`sendToAccount`); when the account is offline the invite simply stays valid until it expires, so a friend who resumes within the window still sees it. `invite.accept {inviteId}` consumes the invite (`takeInvite`) and then **joins through the SAME gates as `room.join`** (`this.join(session, {code})`): an invite saves typing the code and can never bypass the mode, seat or started rules. The sender is told the outcome with `invite.done {inviteId, ok: true, by: name}`, or `{ok: false, reason: <the join error>}`; accepting consumes the invite even when the room refuses the join. `invite.decline {inviteId}` drops it and tells the sender `invite.done {ok: false, declined: true}`. An unknown, foreign, expired or already-consumed invite id answers the same `INVITE_GONE`, so ids cannot be probed for existence. When a room is **disposed**, `dropInvitesForRoom` drops every invite pointing at it and the senders are told `invite.done {ok: false, reason: 'room-closed'}`, because an invite to a dead room would otherwise only fail at accept time.

### 27.8 Threat model and anti-abuse

| attack | mitigation |
|---|---|
| Key guessing / brute force | 160 random bits cannot be enumerated; only the peppered digest is stored; a per-session wrong-key throttle (`maxJoinFails` failures per `joinFailWindowMs`, then `RATE`) stops the hashing, and the account/social token bucket (below) bounds the endpoint; unknown and malformed keys answer the same `ACCOUNT_BAD_KEY` and `login` is a `Map` lookup, so nothing distinguishes "no such account" from "wrong key". |
| Account-name squatting with invisible characters | `normalizeName` (NFKC, `INVISIBLE_RE`, whitespace collapse, trim, 12 code points) removes zero-width/bidi/control characters before anything is stored; `nameKey` makes uniqueness case-folded, so a look-alike name collides → `NAME_TAKEN`; a name with no displayable content is refused. |
| Friend-request spam | The played-together ledger is the only door (`NOT_ELIGIBLE`), a decline sets a 7-day cooldown (`DECLINED`), `MAX_PENDING_REQUESTS` (50) and `MAX_FRIENDS` (100) cap the graph, and every request draws from the social bucket. |
| Invite spam | Per-pair 20 s cooldown (`RATE`), `MAX_INVITES_OUT` (20) / `MAX_INVITES_IN` (10), a 120 s TTL, and the social bucket for `invite.send`. |
| Invite-id probing | A 96-bit random id bound to the recipient; unknown, foreign, expired or replayed ids all answer `INVITE_GONE` (one answer, no existence signal). |
| Room-code brute force | A 4-character code is short, so a failed `room.join` **or `room.spectate`** is counted per session: past `maxJoinFails` (12) inside `joinFailWindowMs` (60 s) the answer is `RATE` instead of `ROOM_NOT_FOUND`, and a success on either clears the counter — neither intent is an oracle for the code space. |
| Presence stalking | Presence is visible to accepted friends only; pushes are coalesced per account and content-deduped; 屏蔽好友 shows only `hidden`; a solo run shows only `solo`; no seat, loadout, host or member detail is ever in the frame. |
| Origin spoofing (share links) | §27.1: strict WHATWG canonicalisation, equality with the connection's own origin, or an EXCLUSIVE `SP_PUBLIC_ORIGINS` allowlist; an origin is never broadcast to another player. |
| Prototype pollution | `__proto__` passes the protocol's id check (it is a legal id string), so every dynamic-keyed collection in `server/accounts.js` (and the lobby's presence/join-fail maps) is a `Map` or a `Set`, never a plain object, and the persisted round trip rebuilds them; `server/net.js isErrCode` also checks own properties so an inherited name like `constructor` is not an error code. |
| Persistence corruption | Any unreadable, oversized (> `MAX_ACCOUNT_FILE_BYTES`, 64 MiB), unparseable, non-object or **newer-version** file is renamed to `${file}.corrupt-<timestamp>` (`#quarantine`) and the server starts empty — the file is never overwritten and the evidence is kept. A changed `SP_KEY_PEPPER` is detected through the file's `pepperTag`, logged loudly and **kept in the file** (its tag is written back unchanged) so the warning repeats on every boot until the operator restores the pepper or deletes the file; `#quarantine`'s aside name carries a random suffix (two bad files in the same millisecond cannot clobber each other) and the size cap is measured in bytes. Writes are atomic (temp file + rename) with mode **0600**, debounced (`saveDelayMs` 1500) and flushed at shutdown; the file holds **digests only**. A hand-edited file cannot install a friendship: on load every friend edge must exist on **both** sides (and every pending request must mirror), non-existent ids are dropped, and `maxAccounts` / `maxFriends` / `MAX_PENDING_REQUESTS` / `maxMet` are clamped to the documented limits rather than trusted. |
| Unbounded growth | Every collection has a cap: accounts (5000), friends (100), met ledger (200), pending requests (50), invites out/in (20/10), the invite-cooldown map (4096), the per-network creation windows (4096), the presence/throttle maps (4096), the decline-cooldown map per account (pruned by `DECLINE_COOLDOWN_MS`, capped at `MAX_PENDING_REQUESTS`), and the file itself (64 MiB). |

The account/friend/invite/share intents have their own token bucket, separate from the battle and heavy-op buckets: `NET_DEFAULTS.socialPerSec` = **2** and `socialBurst` = **10**, over `SOCIAL_TYPES` = `account.create/login/rename/rotate/logout`, `friend.request/accept/decline/remove/sync`, `invite.send/accept/decline` and `share.link`. A normal UI pass (create → sync → request → accept → invite) fits in the burst; a hammering socket gets `RATE`.

### 27.9 Configuration

- **`SP_ACCOUNTS_FILE`** — where the account file lives. `npm start` passes `defaultAccountsFile()` (`server/index.js`), which is `state/accounts.json` under the repository and is created automatically; the value overrides it, and exactly `off` / `0` keeps everything **in memory**. A programmatic `startServer()` stays in memory unless it is given `accountsFile` — which is what tests get, so no test writes into the repository. `startServer()` returns the `AccountStore` as `accounts` (tests and `/healthz` counters; `npm start` flushes it at shutdown). The whole `state/` directory is git-ignored; the file holds key **digests** and the social graph, never a key.
- **`SP_KEY_PEPPER`** — the secret mixed into every key digest (`accountOptionsFrom`). It must be set on a real deployment and must stay **stable**: changing it (or moving the file to another deployment that uses a different one) invalidates every existing key's ability to log in, which the store warns about through `pepperTag`.
- **`SP_PUBLIC_ORIGINS`** — a comma/space-separated list of canonical origins for share links (`shared/origin.js parseOriginList`; invalid entries are dropped and logged). When non-empty it is **EXCLUSIVE**: only a listed origin can be handed out.
- **`SP_SHARE_LINK=0`** — no server opinion at all (`source: 'none'`); the client builds the link from its own `location.origin`. Unset/empty means on.
- **`TRUST_PROXY`** — `auto` (default: only loopback/private peers are trusted to report `X-Forwarded-Host` / `X-Forwarded-Proto`; the same rule as `X-Forwarded-For`/`X-Real-IP`), `1`/`true` (always trust the proxy), or `0`/`false` (never). A wrong value only ever changes which address a connection claims for itself; the §27.1 equality/allowlist rule is what decides whether that address may be handed out.
- **`socialPerSec` / `socialBurst`** — the account/social token bucket (default 2/s, burst 10), overridable through `startServer()`. The lobby's `friendPushMs` (1000), `maxJoinFails` (12) and `joinFailWindowMs` (60 000) are also lobby options.

### 27.10 The wire

C→S (client → server): `hello {name, token?, version?, key?, origin?}` (the two new optional fields carry the account key and the page's own origin) · `account.create {name}` · `account.login {key}` · `account.rename {name}` · `account.rotate {}` · `account.logout {}` · `friend.request {accountId}` · `friend.accept {accountId}` · `friend.decline {accountId}` · `friend.remove {accountId}` · `friend.sync {}` · `invite.send {accountId}` · `invite.accept {inviteId}` · `invite.decline {inviteId}` · `share.link {}`.

S→C (server → client): `welcome` gains `account`, `accountError` and `shareOrigin` (the per-connection share-link answer) · `account.state {account, key?}` (the key rides only on create/rotate; `key` is `undefined` otherwise) · `friend.state {account, friends, incoming, outgoing, met, invites}` (the whole snapshot) · `friend.request {accountId, name, at}` · `friend.update {accountId, name, online, status, room}` (an increment of `friends`) · `friend.remove {accountId, name}` · `invite {inviteId, from, fromName, code, mode, difficulty, players, at, expiresAt}` · `invite.done {inviteId, ok, by?, declined?, reason?}`. `share.link`'s answer is the `ok` payload `{origin, url, code, source}` (`server/net.js okMsg` merges a handler's `payload` into the `ok` frame; `t` and `rid` can never be overridden). Close code **4004** is sent to the other sessions of an account whose key was rotated (`CLOSE.ROTATED`, "account key rotated"); `4001` still means the session was taken over by another socket, and `welcome.accountError` carries `ACCOUNT_BAD_KEY` / `RATE` / `INTERNAL` for a refused `hello.key`. Guests simply never see `account.state`/`friend.state` with an account, and every social intent answers `ACCOUNT_REQUIRED`.
